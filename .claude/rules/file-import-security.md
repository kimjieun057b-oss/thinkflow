# 파일 업로드·분석·보안 규칙 (PRD 5.3, 8, 15.1-15.2, 16장 기반)

## 지원 파일 (MVP)

| 형식 | 우선순위 | 용도 |
| --- | --- | --- |
| .md | P0 | PRD, API 명세 |
| .sql | P0 | DB 스키마 |
| .json | P0 | 구조화된 데이터 |
| .pdf | P0 | 설계 문서 |
| .yaml/.yml, .docx, .ts/.tsx | P1 | MVP 이후 확장 |

## 업로드 정책

- 파일 개수 및 용량 제한을 서버에서 강제한다.
- 허용 확장자 검증 **및** 실제 MIME 타입 검증을 모두 수행한다 (확장자만 믿지 않음).
- 손상된 파일/파싱 실패는 개별 파일 단위로 처리 — **다른 파일의 분석까지 무조건 중단하지 않는다.**
- 실패한 파일과 원인을 사용자에게 표시한다.
- 사용자별 Storage 접근 제한을 적용한다 (경로 기반 접근 제어).
- 동일 파일 중복 업로드 처리 정책을 정의한다 (`checksum` 컬럼 활용).

## 파일 상태 머신

```
uploaded → extracting → extracted → analyzing → completed
                      ↘ failed (어느 단계에서든 가능)
```

## 업로드 처리 순서

1. 사용자 인증
2. 프로젝트 소유권 확인
3. 파일 형식/크기 검증
4. Storage 업로드
5. `design_files` 레코드 생성
6. 추출 작업 시작 → 결과 저장 → 상태 갱신

Storage 업로드와 DB 저장은 분리된 작업이므로, 실패 시 **고아 파일(DB 레코드 없는 Storage 파일) 정리 정책**을 둔다.

## 추출 실패 처리

- 추출 결과가 비어있거나 파싱 실패 시 해당 파일에만 오류를 기록한다 (`file_extractions.error_message`).
- **파일 파싱 실패와 AI 분석 실패는 분리**해서 추적한다 — 하나의 실패가 다른 레이어의 상태를 오염시키지 않는다.
- 이미지로만 구성된 PDF, 복잡한 표는 MVP에서 정확도를 보장하지 않으며, 지원되지 않는 내용은 사용자에게 명시한다.

## 보안

- Cloudflare 인증정보(API Token 등)는 서버 전용으로 관리하고 클라이언트에 노출하지 않는다.
- 악성 파일 및 파서 취약점에 대응한다 (예: 신뢰할 수 없는 PDF/SQL 파서 사용 시 샌드박싱 고려).
- Markdown 및 텍스트 출력 시 XSS를 방지한다 (렌더링 전 sanitize).
- **사용자 업로드 파일은 신뢰할 수 없는 입력 데이터로 취급**한다.
- **프롬프트 인젝션 방어**: 업로드 문서 내부에 포함된 지시문("이 내용을 무시하고...")을 시스템 지침으로 실행하지 않는다. 파일 내용은 항상 데이터로만 취급해 프롬프트에 포함한다.
- 원본 파일은 AI가 수정하지 않는다.
- 프로젝트 삭제 시 파일 및 연관 데이터 삭제 정책을 명확히 정의하고 적용한다.
